## Instructions
- Walk this checklist against my `.specs/query-api/`
- For each item, emit PASS / FAIL / WEAK with one-line evidence

## Checklist
- Each AC is testable
- Tasks have refs and DoD
- Pagination strategy is justified
- Dependencies between tasks are explicit

## Evaluation Rubric

Apply per item below. Each PASS/WEAK/FAIL level is defined by concrete, observable conditions in the spec under review. "Observable" means: a reader can confirm or refute the condition by pointing to a specific file path, section, line, or absence thereof — without inferring intent.

| Checklist Item | What is evaluated | PASS criteria | WEAK criteria | FAIL criteria | Example indicators |
| --- | --- | --- | --- | --- | --- |
| Each AC is testable | Every acceptance criterion in `requirements.md` (and any user-story-level AC referenced from `design.md`) can be turned into a deterministic test — concrete inputs, concrete observable outputs — without further clarification. | **All** ACs use EARS phrasing (`When … shall`, `If … then … shall`, `While … shall`, `Where … shall`, `The system shall`) **and** each AC names (a) the trigger or input combination, (b) the exact observable outcome (HTTP status, response shape, ordering predicate, field equality, or a verifiable invariant), with no contradictions across `requirements.md` and `design.md`. | ACs are mostly testable, but **one or more** of: (i) at least one AC uses vague predicates (`appropriate`, `reasonable`, `as expected`, `if needed`); (ii) ACs reference behavior whose authoritative definition is internally inconsistent between `requirements.md` and `design.md`; (iii) at least one AC requires the reader to infer the expected output. | Multiple ACs lack observable outputs, rely on subjective wording, do not follow EARS, or describe intent without naming the system's response. A tester would have to invent the expected behavior. | PASS: `the system shall return HTTP 200 with data: [] and nextCursor: null`. WEAK: AC defined as `the system shall paginate efficiently`. FAIL: `the system handles large queries`. |
| Tasks have refs and DoD | Each task entry in `tasks.md` cites the spec source it implements **and** carries an explicit, per-task Definition of Done that lists what must be true to merge it. | **Every** task in `tasks.md` has both (a) a specific spec reference — a `requirements.md §x.y` / `User Story N` / `design.md §x.y` citation (or equivalent), not a whole-document link — **and** (b) a per-task DoD enumerated *in `tasks.md` itself* (e.g., a `Definition of Done:` block, an `Acceptance:` list, or per-task verification bullets). The uniform preamble line ("compiles, `mvn verify` is green") alone is not sufficient because it does not vary by task. | One of: (i) refs are present but coarse (e.g., link to a whole document instead of a section); (ii) DoD is present only as a uniform preamble line or a single bullet shared across all tasks; (iii) DoD is delegated to external files (e.g., `plans/Tx-plan.md`) rather than being in `tasks.md`; (iv) at least one task is missing either ref or DoD. | One or more tasks have no spec ref and no DoD at any granularity, or `tasks.md` explicitly states it omits DoD with no replacement inside the file. | PASS: `T2 — implements design.md §6 + US3.4. DoD: \`from > to\` returns 200/[]/null; > 90 days returns 422; IT covers both.` WEAK: only a preamble `mvn verify` line + `Definition of Done details are intentionally omitted`. FAIL: `Implement pagination.` (no ref, no DoD). |
| Pagination strategy is justified | `design.md` (or `requirements.md`) explicitly names the chosen pagination approach, names at least one alternative considered, and ties the choice to the spec's requirements / invariants. | The chosen approach is named (e.g., **keyset / seek**, offset/limit, page-token); at least one alternative is named and rejected; the choice is justified by **≥2 concrete arguments** that each tie to a stated requirement or invariant (e.g., concurrent-insert stability vs. US3 exactly-once; O(1) scan vs. NFR latency; cursor opacity vs. evolvability). Trade-offs and limitations (e.g., one extra empty page at end-of-set) are stated. | The strategy is named and one rationale is given, but: (i) no alternative is named, **or** (ii) only one argument is offered, **or** (iii) trade-offs / limitations are absent, **or** (iv) the argument restates a requirement instead of explaining why the chosen mechanism delivers it. | No discussion of why the chosen approach was selected; pagination is described purely as "how it works" with no comparison or rationale. | PASS: `§4.2 Keyset, not offset — stability under concurrent appends; O(1) vs. O(n) deep-page cost; opaque cursor allows internal changes`. WEAK: `we use keyset pagination because it is more efficient`. FAIL: `pagination is done via cursors`. |
| Dependencies between tasks are explicit | `tasks.md` makes the build/merge order of tasks unambiguous: each task states what it depends on, and the relationships are visible at a glance. | **Both** present: (a) every task carries a `Dependencies` line citing predecessor task IDs (or explicitly says `Dependencies: none`); (b) a dependency graph or merge-order diagram lists all tasks and matches the per-task statements; (c) each non-trivial dependency identifies *what* is depended on (artifact, type, port method, migration), not just that one exists. | One of: (i) per-task `Dependencies` lines exist but no overview graph/order exists (or vice versa); (ii) graph and per-task lines disagree; (iii) dependencies are stated but never say *what* is depended on; (iv) one or more tasks are missing a dependency statement. | No dependency information at all — tasks are presented as a flat list with no ordering, and a reader cannot tell which task must land first. | PASS: per-task `**Dependencies.** T1 (uses AuditEventQuery, KeysetPosition, LoadAuditEventPort.find)` + ASCII graph `T1 → T2 → T4`. WEAK: graph only, with no per-task statements. FAIL: tasks T1…T5 listed without ordering or `Dependencies` lines. |

### How to evaluate

1. For each checklist item, walk the four criteria columns top to bottom and stop at the first level whose conditions hold against the spec under review.
2. When in doubt between two levels, choose the lower one (WEAK over PASS; FAIL over WEAK).
3. Cite specific files, sections, or absences as evidence in the report — never a generic "looks good".
4. If the spec internally contradicts itself on the point being evaluated, that is automatically not PASS for the affected item (it is at most WEAK).
